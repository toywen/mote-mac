# 0025 同步从第一版就按账户建模，登录界面留到以后

- 状态：被 0029 替代（登录部分）
- 日期：2026-11-23

## 背景

[ADR 0024](0024-no-account-system-in-v1.md) 决定第一版不做账户体系，只用设备令牌。

2026-11-23 你提出需要账户体系。理由是 Mac 端和 iOS 端的设备 id 不同，没有账户，两边的笔记怎么算同一份。

先澄清一点：设备 id 不同不影响同步。同步服务的文件不按设备存。一台设备上传后，同一服务的所有设备都能拉到。设备令牌只是访问的钥匙，两把钥匙开同一扇门。

但按账户建模仍然值得做，有三个原因：

1. 以后 iOS 版、第二台 Mac、第二台笔记库都会出现。到时候再改数据模型，要迁移已有数据。
2. 以后想分享笔记库给别人，账户是最小单位。
3. 现在建模的代价很小：加两张表和一个字段，不用做登录界面。

## 决定

- 同步服务从第一版就按账户建模。数据模型是三层：账户 → 笔记库 → 文件。设备挂在账户下。
- 第一版只有一个账户，由服务器命令行创建。没有注册、登录、找回密码和邮箱验证。
- 设备令牌对应一个账户。客户端不需要传账户编号。服务端按令牌找到账户，再检查请求里的笔记库是否属于这个账户。
- 协议里每个请求带笔记库编号和版本号。版本号按笔记库算。
- 客户端第一次连上时，服务端返回这个账户下的笔记库列表。只有一个时自动选中。
- 存储按笔记库分表：文件表和历史版本表都有笔记库编号这一列。内容按哈希存在所有笔记库共用的内容目录，同一个内容只存一份。

以后加登录时这样做：

- 服务端加登录接口，返回会话或长期令牌。
- 客户端加登录界面，登录后拿到设备令牌，流程和现在一样。
- 数据模型不用迁移，只加账户创建和邀请的接口。

## 理由

- 账户是数据归属的最小单位。设备只是访问账户的钥匙，换设备、加设备都不改数据归属。
- 现在加两张表的成本是一个下午；等两边都有数据再迁移，成本和风险都大得多。
- 不做登录界面，第一版的使用方式和没有账户时一样：服务器上跑一条命令，拿到令牌填进 mote。

## 后果

- 服务器上多两张表：账户表和笔记库表。
- 版本号从一个序列变成按笔记库分开。协议里多一个笔记库编号字段。
- 第一版仍然没有注册和登录。第二条笔记库要在命令行里创建，设备的令牌还是命令行打印。
- 想分享笔记库给别人，要等登录和邀请接口做出来。
