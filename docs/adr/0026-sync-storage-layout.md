# 0026 同步服务用 SQLite 存元数据，内容按哈希存磁盘

- 状态：已接受
- 日期：2026-11-23

## 背景

[ADR 0022](0022-sync-service-deployment-and-latency.md) 定了部署和容器。这篇定存储形态，要回答两个问题：元数据放哪，文件内容放哪。

2026-11-23 实测 `~/life-os`：除 `.git` 和 `.obsidian` 外约 8M，214 个文件，141 篇笔记。最大内容文件 3.3M。按 30 天保留历史估计，服务端稳定在 100 到 200M。

候选方案：

| 方案                            | 好处                                 | 代价                                   |
| ------------------------------- | ------------------------------------ | -------------------------------------- |
| SQLite 存元数据，内容存磁盘文件 | 读写在本机，备份小，坏一个不影响别的 | 读一个文件要两步：先查表，再读文件     |
| 内容和元数据都放 SQLite         | 一个文件就是全部                     | 数据库膨胀，大字段占内存，写入互相等待 |
| OSS 当存储本体                  | 不占服务器磁盘                       | 延迟回来，多一个故障点，两处状态要一致 |
| 不用 OSS，只留本地              | 最简单                               | 服务器磁盘坏了，历史版本全丢           |

## 决定

- **元数据用 SQLite。** 表有 `users`、`vaults`、`devices`、`files`、`revisions`、`blobs`。数据库开 WAL 模式，设 5 秒 busy timeout。
- **内容按哈希存磁盘。** 路径是 `/data/blobs/<哈希前两位>/<SHA-256>`，所有笔记库共用。同一个内容只存一份。
- **先写内容，再提交事务。** 崩溃最坏的结果是一个没人引用的内容文件，清理任务会回收它。
- **不用 OSS。** 第一版既不用它当存储本体，也不做备份，见 [ADR 0027](0027-no-backup-in-v1.md)。内容超过服务器磁盘，或者开多台同步服务要共享内容时，再重新评估。
- **驱动待定。** `better-sqlite3` 和 Node 自带的 `node:sqlite` 二选一,在单元 B 开始时确定。

## 理由

- 内容只有一两百 M，磁盘放得下。为此把读写搬到网络上，换不到好处。
- SQLite 一次只让一个写事务进行。传一个 50M 的附件时，如果内容在数据库里，所有笔记的提交都会被挡住。
- 内容寻址让去重免费：同一张图片存两次只占一份，历史版本也只加引用不加内容。
- 内容和数据库分开,`fsck` 能逐个比对。数据库坏了,内容还在磁盘上。
- 第一版不做备份，理由见 ADR 0027。

## 后果

- 读一个文件两步：先查 `files` 表拿哈希，再读 `blobs/`。
- 服务器磁盘坏了,内容全丢,历史版本也丢。每台设备的本机笔记库是完整副本,笔记本身不会丢。
- 服务器磁盘用量估计 100 到 200M,远低于 8G 上限。磁盘不是要盯的问题。
- 每天要跑清理任务：先删过期历史版本，再删没被引用的内容。
