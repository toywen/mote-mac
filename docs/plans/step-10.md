# 第 10 步实现计划

本计划实现[功能列表](../features.md#第-10-步同步)里的第 10 步：同步。决定见 [ADR 0021](../adr/0021-own-sync-service-without-claude-connector.md) 到 [ADR 0025](../adr/0025-accounts-in-data-model-from-v1.md)。术语见 [CONTEXT.md](../../CONTEXT.md#同步)。

完成标准有三条：

- 同步-1：两个设备同时改同一篇笔记，合并后不丢字。
- 延迟：一台设备停止输入后 3 秒内，另一台设备的磁盘上出现改动。目标是约 2 秒。
- 不伤 ERP：同步服务上线前后，ERP 的 4 个容器状态不变。

## 两个仓库

代码分在两个仓库，见 [ADR 0023](../adr/0023-sync-repo-split.md)：

```
mote-sync(新仓库)                   mote-mac(现有仓库)
├─ protocol/   mote-sync-protocol  ├─ src/main/sync.ts   同步模块
│    类型、合并规则、协议说明         ├─ src/core/sync/    只放转接代码
├─ server/     同步服务             └─ 依赖 mote-sync-protocol
└─ Containerfile
```

- 协议包里不引用 Node 和 Electron 的 API。Mac 端和服务端都能用它。
- 协议包改版本时，在 `mote-mac` 里升级依赖。只做加法，见 ADR 0023。

## 结构

```
设备（Mac 端 mote 主进程）                    同步服务（阿里云，Podman 容器）
┌──────────────────────────┐                ┌───────────────────────────┐
│ Vault：磁盘读写、文件监听   │                │ 文件表（SQLite）            │
│      │                    │   HTTPS        │   路径、哈希、版本号、已删   │
│ 同步模块                   │ ◀────────────▶ │ 账户表、笔记库表（SQLite）   │
│   上传队列：笔记、附件各一个 │   上传、拉取    │   设备表（SQLite）            │
│   同步状态表               │                │ 内容目录：按哈希存文件内容   │
│                           │   WebSocket    │                           │
│                           │ ◀───────────── │ 接受改动后通知其他设备       │
└──────────────────────────┘   只推版本号    └───────────────────────────┘
```

每份状态只有一个持有者：

| 状态                           | 持有者   | 存在哪                                                   |
| ------------------------------ | -------- | -------------------------------------------------------- |
| 账户、笔记库和设备             | 同步服务 | `/srv/mote-sync/sync.db`                                 |
| 每个文件的最新哈希和版本号     | 同步服务 | `/srv/mote-sync/sync.db`                                 |
| 历史版本                       | 同步服务 | `/srv/mote-sync/sync.db` 和 `/srv/mote-sync/blobs/`      |
| 同步状态表                     | 同步模块 | `~/Library/Application Support/mote`，每个笔记库一个文件 |
| 服务器地址、证书指纹、设备令牌 | 同步模块 | `~/Library/Application Support/mote/settings.json`       |

同步模块不存同步基准的内容。要合并时，它按同步状态表里的哈希向同步服务要。

## 同步流程

### 上传

1. 文件监听报告一个文件变了。
2. 同步模块等这个文件 1.5 秒没有变化。
3. 同步模块算它的哈希。哈希和同步状态表里的一样，就停。
4. 同步模块上传内容。同步服务已有这个哈希的内容时，跳过上传。
5. 同步模块提交改动：路径、新哈希、同步状态表里的版本号。
6. 同步服务比较这个版本号和该文件的最新版本号。
   - 一样：接受，版本号加 1，返回新版本号，通知其他设备。
   - 不一样：拒绝，返回最新的哈希和版本号。
7. 被接受：同步模块更新同步状态表。被拒绝：走"合并"。

### 下载

1. 同步模块收到通知，或者刚连上同步服务。
2. 同步模块拉取"某个版本号之后的所有改动"。
3. 对每个改动，同步模块比较本机文件的哈希和同步状态表里的哈希。
   - 一样：本机没改过。下载内容，写进笔记库，更新同步状态表。
   - 不一样：本机也改过。走"合并"。
4. 写进笔记库走 `Vault` 的写入队列，和保存、改名排在一起。打开着的笔记按外部修改处理。

### 合并

| 情况                                    | 做法                                               |
| --------------------------------------- | -------------------------------------------------- |
| 笔记，能拿到同步基准                    | 三方合并。写进笔记库，再提交                       |
| 笔记，拿不到同步基准，或不是 UTF-8 文本 | 本机内容存成冲突文件。原文件换成远程内容           |
| 附件                                    | 后提交的赢。本机内容重新提交，远程内容成为历史版本 |
| 一边删除，一边修改                      | 修改赢。文件保留                                   |
| 两边都删除                              | 记为已删                                           |

三方合并按行比较。两边改了同一段时，两段都保留，本机的在前。

### 第一次同步

设备第一次连同步服务时，同步状态表是空的。同步模块逐个路径比较：

| 本机 | 同步服务     | 做法           |
| ---- | ------------ | -------------- |
| 有   | 没有         | 上传           |
| 没有 | 有           | 下载           |
| 有   | 有，哈希相同 | 只写同步状态表 |
| 有   | 有，哈希不同 | 生成冲突文件   |

### 删除和改名

- 同步状态表里有、磁盘上没有的文件，同步模块提交删除。
- 同步服务不真删内容。它把文件标为已删，内容留作历史版本。
- 改名当作删除加新建。哈希相同，所以不用重新上传内容。
- **删除保护**：一次扫描发现超过 20 个文件且超过一半的文件被删时，同步模块停下来问你。笔记库文件夹没挂载或被清空时，这条规则防止把删除同步出去。

### 断线

- 设备每 30 秒发一次心跳。两次没回应就重连。
- 重连的等待时间从 1 秒开始，每次加倍，最长 60 秒。
- Mac 唤醒和网络恢复时立刻重连。
- 重连后先下载，再上传。

## 账户

按账户建模，见 [ADR 0025](../adr/0025-accounts-in-data-model-from-v1.md)。数据模型有三层：

```
账户 ──┬─ 笔记库 ── 文件、历史版本
       └─ 设备
```

- 每个请求带设备令牌和笔记库编号。服务端按令牌找到账户，再检查这个笔记库属于这个账户。
- 版本号按笔记库算。一个笔记库一个序列。
- 第一版只有一个账户，由服务器命令行创建。没有注册和登录。
- 设备由服务器的命令行新建和撤销。命令行只打印一次令牌。
- Mac 端把令牌存进系统钥匙串。设置界面只显示"已连接",不回显令牌。
- 客户端连上后，服务端返回账户下的笔记库列表。只有一个时自动选中。

这样 Mac 端和 iOS 端各用自己的设备令牌，但属于同一个账户、同一个笔记库。两边的设备 id 不同，数据仍然是一份。

以后加登录时只加接口和界面，数据模型不用迁移。

## 单元 A：三方合并和共用类型

- 放在 `mote-sync` 仓库的 `protocol/` 目录。它不引用 Node 和 Electron 的 API，也不引用文件系统。
- `merge.ts`：输入同步基准、本机内容、远程内容，输出合并后的内容。
- `path.ts`：路径规则。相对路径、`/` 分隔、不超过 1024 字节；拒绝 `..`、反斜杠和所有以 `.` 开头的段。唯一的例外是 `.mote/attachments/` 下面，见 [CONTEXT.md](../../CONTEXT.md#同步)。
- `protocol.ts`：设备和同步服务之间的请求和回应的类型。类型只写在这里，文档不抄。
- `README.md`：协议说明。iOS 版按它用 Swift 实现，所以每个请求、回应和错误码都要写全。
- 合并前把内容变成规范化文本。合并后还原本机文件的 BOM 和换行符。
- 单元 A 结束时打第一个标签并发布协议包，单元 C 才能安装它。
- 证明：
  - 固定用例：只有一边改、两边改不同段、两边改同一段、一边删一段另一边改这段。
  - 随机测试：随机生成基准和两边的插入。检查两边插入的每一段文字都在结果里。

## 单元 B：同步服务

- 放在 `mote-sync` 仓库的 `server/` 目录，自己的 `package.json`。它依赖 `mote-sync-protocol`。
- 一个 Node 进程。HTTPS 和 WebSocket 用同一个端口。
- 存储：SQLite 存账户表、笔记库表、文件表、历史版本表和设备表，开 WAL 模式。内容按哈希存在 `/data/blobs/<哈希前两位>/<SHA-256>`，所有笔记库共用，同一个内容只存一份。见 [ADR 0026](../adr/0026-sync-storage-layout.md)。
- 提交顺序：先写内容文件，再进数据库事务。崩溃最多留下没人引用的内容文件，由清理任务回收。
- 上传和下载内容用流，不把整个文件读进内存。同步服务边收边算哈希，哈希不对就丢掉。
- 设备表只存设备令牌的哈希。服务端按令牌找到账户，检查请求的笔记库属于这个账户。
- 存储上限：同步服务记录内容目录的总大小。超过上限时拒绝上传。
- 清理：每天删过期的历史版本。笔记留 30 天，附件留 14 天。没有文件引用的内容一并删除。
- 命令行：创建账户，创建笔记库，新建设备并打印设备令牌，撤销设备，打印证书指纹。
- 证明：
  - 提交带旧版本号被拒绝。
  - 两个连接同时提交同一个文件，只有一个被接受。
  - 提交后，另一个连接收到通知。
  - 没有设备令牌或令牌错的请求被拒绝。
  - 另一个账户的设备令牌请求这个笔记库，被拒绝。
  - 超过存储上限时上传被拒绝。
  - 哈希不对的内容被拒绝。

待核实：SQLite 用 Node 自带的 `node:sqlite` 还是 `better-sqlite3`。前者不用编译原生模块，但在 Node 22 里还标着实验性。单元 B 开始时查文档再定。客户端的状态文件不用 SQLite，用 JSON，见单元 C。

## 单元 C：同步模块

- 放在 `src/main/sync.ts`。它依赖 `mote-sync-protocol`，不引用 Electron，所以 `tools/sync-sim.mjs` 能直接跑它。
- 协议包发布到 npm 前，用 `vendor/` 里的 tarball，由 `tools/update-sync-protocol.mjs` 刷新。发布后换成 npm 上的版本。主进程构建时把它打进包里。
- 它通过 `Vault` 读写笔记库，不自己碰磁盘。写入走 `Vault` 的写入队列。
- 它用 `ws` 包连 WebSocket，用 Node 的 `https` 发请求。两处都做证书固定。
- 它跳过以 `.` 开头的目录，`.mote/attachments/` 除外。
- 它记下自己写进笔记库的文件的哈希。文件监听报告这些文件时，它不再上传。
- 笔记库的不变式要加一条：同步模块可以写笔记库。实现时在同一个改动里更新 `ARCHITECTURE.md`。
- 这个单元改 `src/main/vault.ts` 的队列和文件监听。改之前和改之后都跑 `verify-open-note`。
- 证明用 `tools/sync-sim.mjs`。它起一个本机同步服务和两个模拟设备，各用一个临时笔记库：
  - 设备甲改一篇笔记，设备乙的磁盘在 3 秒内出现同样的字节。
  - 两个设备断线后各改同一篇笔记的不同段，重连后两边内容相同，两边的改动都在。**这条是同步-1 的证据。**
  - 两个设备各改同一段，重连后两段都在。
  - 设备甲删除、设备乙修改同一篇笔记，文件保留。
  - 设备甲改名，设备乙出现新名字，没有重新上传内容。
  - 一个 50M 的附件在上传时，笔记的延迟仍在 3 秒内。
  - 清空设备甲的笔记库文件夹，同步模块停下，设备乙的文件都在。
  - 没改过的文件，同步前后 `tools/hash-vault.mjs` 的结果相同。

## 单元 D：设置界面和同步状态显示（已完成 2026-11-24）

结果：设置面板、侧栏状态行、删除保护对话框、主进程的 `SyncController`，以及真实的 Playwright 测试 `tests/e2e/sync.spec.ts`。顺带修了一处主进程的旧问题：`vaults` 原来用对话框给的路径做键，`Vault` 内部用 realpath，两者不同，导致按窗口的笔记库找不到同步控制器；现在统一用 realpath。

- 设置里填两项：服务器地址、证书指纹。设备令牌单独存进钥匙串，设置界面只显示"已连接"。
- 连上后显示账户下的笔记库。只有一个时自动选中。
- 窗口里显示同步状态：已同步、同步中、离线、出错。
- 删除保护触发时弹出对话框，让你选继续或停止。
- IPC 的类型加在 `src/core/ipc.ts`。
- 证明：Playwright 测试连本机同步服务。填设置后状态变成已同步；停掉同步服务后变成离线。

## 单元 E：部署到阿里云

> **2026-11-25**：现阶段改走 HTTP，不要证书，见 ADR 0030。下面的证书和指纹步骤留作记录。服务端去掉 `TLS_CERT` 和 `TLS_KEY` 就是 HTTP，端口不变。

> **状态（2026-11-24）**：已部署。服务器 Ubuntu 22.04、podman 3.4.4、1.7G 内存、16G 可用磁盘，和 ERP 同机。容器 300M 内存上限，数据在 `/srv/mote-sync`，用 systemd 单元和每日 03:17 的 gc 定时器，见 mote-sync 仓库的 `deploy/`。证书是自签的，指纹 `31:14:F8:FB:…:8D:AD:E2`。8443 已在本机通，安全组放行后从 Mac 用真实 App 注册也能同步（`tests/e2e/live.spec.ts`，6.8 秒）。踩到两个坑：podman 3.4.4 建的自定义 CNI 网络它的 firewall 插件读不懂，容器起不来，改用默认 bridge；`serve` 要求数据目录里已有 `sync.db`，安装脚本要先跑 `init`。

2026-11-24：单元 F 前两步通过。`~/life-os` 副本（135 个文件，哈希用 `tools/hash-vault.mjs`）同步上去后完全一致；空的第二台设备同步下来也完全一致。首次上传 5.4 分钟，量到瓶颈是每个文件 3 次请求、每次往返 0.4–1.7 秒，而同步通道是串行。改成每个文件一条队列、最多 8 个并发后降到 1 分钟（附件通道 2 个并发），`MOTE_SYNC_NOTE_CONCURRENCY` 可调。

原计划：

部署前先在服务器上查两件事：

```sh
podman --version
lsblk
```

第一条决定用哪种方式让容器开机自启。第二条确认有没有另一块数据盘。

步骤：

1. 写 `mote-sync` 仓库的 `Containerfile`。镜像推到已经在用的阿里云容器镜像仓库。
2. 在服务器上建 `/srv/mote-sync`。
3. 在服务器上生成自签证书和私钥，放在 `/srv/mote-sync`，只有 root 可读。
4. 起容器：内存上限 300M，端口 8443，挂载 `/srv/mote-sync`，用自己的容器网络。
5. 让 systemd 管这个容器，服务器重启后自动起来。
6. 在阿里云安全组放行 8443 端口的入方向。
7. 新建一个设备，记下设备令牌和证书指纹。

证明：

- 部署前后各跑一次 `podman ps`。ERP 的 4 个容器都在，启动时间没变。
- 从 Mac 用证书指纹和设备令牌连通。用错的指纹连接被设备拒绝。
- 重启同步服务的容器，ERP 不受影响，设备自动重连。
- 删掉容器，按同样的参数重建，`/srv/mote-sync` 里的数据都还在。第一版不做备份，见 [ADR 0027](../adr/0027-no-backup-in-v1.md)。

## 单元 F：在副本上试，再切换

1. 拷一份 `~/life-os` 做副本。用 `tools/hash-vault.mjs` 记下哈希。
2. 让副本做第一次同步。再跑 `tools/hash-vault.mjs`，结果必须相同。
3. 让第二个模拟设备从空文件夹同步下来。它的哈希必须和副本相同。
4. 在 `~/life-os` 上开同步。obsidian-git 继续开着，并行跑一周。
5. 一周内没有丢字、没有多出的冲突文件，就关掉 obsidian-git。
6. 更新 `docs/features.md` 里同步-1 的状态和证据，把 ADR 0021 到 0025 的状态改成"已实现"。ADR 0024 保持"被 0025 替代"。
